# Acceptance report format

Read when writing or updating an acceptance `report.md`. The report reuses the parts of pr-review-guide's [review report format](../../pr-review-guide/references/report-format.md): the [attention items](../../pr-review-guide/references/report-format.md#item-shape), the [requirements and verification tables](../../pr-review-guide/references/report-format.md#requirements-and-verification-tables), and the [bug cards](../../pr-review-guide/references/report-format.md#bug-cards). This file states only what differs; where it is silent, that format applies. `render_page.py --check --acceptance` checks the structure below, not whether a requirement is met; every claim stays bounded by its [evidence](../../EVIDENCE.md).

For a new report, fill [report-template.md](report-template.md). Replace every prompt, repeat sources, rows, items, and cards as needed, and remove each line or paragraph whose prompt names a condition that does not hold, such as the `base` line when no base is pinned.

## Shape

Use these headings as written and in this order, because the checker looks for them:

- **Front matter** — flat `key: value` lines only: `head` (full SHA, required), `base` (full SHA, only when pinned), and `repository: owner/name`. Intent sources go under *Provenance*, never in front matter.
- **Title** — `# <what was checked, as a short statement>`.
- **Bottom line** — the paragraph under the title, starting `**Bottom line:**`: counts by status, blockers, and the first action. It gives no merge or ship verdict.
- **Reviewed and coverage** — `**Reviewed:**` names the head, the base or `no base`, and the collection time; `**Coverage:**` names the sources reached and missed, the depth, and material gaps.
- `## What was asked` — one paragraph: the intent sources, what they ask for, and the feature scope, each cited.
- `## What to look at` — pr-review-guide's attention list, with the same *what to do* and *how we know* phrases. Rank Unmet rows first, then Partial rows, then bugs that break a requirement, then Needs clarification rows, then the rest.
- `## Requirements` — [grouped by source](#requirements).
- `## Nobody asked for this` — [listed or none found](#nobody-asked-for-this).
- `## Possible bugs` — pr-review-guide's bug cards, with the [acceptance origins](#bug-origins).
- `## Questions for the author` — [two lists](#questions-for-the-author).
- `## Verification` — pr-review-guide's verification section unchanged, including the *Bug probes* row.
- `## Evidence and record` — [three subsections](#evidence-and-record).
- `## Status and label key` — generated by `--sync-labels`.

## Requirements

Put one `### <source title>` per issue, ticket, or spec, each title distinct, and under it pr-review-guide's four-column table. Each row is one observable condition, quoted and linked to its specific source: the issue, comment, ticket field, or plan heading. Label a requirement inferred from description prose *inferred*. A row merged from several sources sits under one source heading and links every source. Text between `## Requirements` and the first source heading is prose only: when the list was not confirmed, one paragraph there states that and invites correction.

- The intent cell links its source, unless the row is Needs clarification for missing intent.
- The evidence cell links pinned source, a run record, or a bug card, or states an explicit gap: `not verified`, `not inspected`, or `unknown`. A Met row links pinned source or a run record. An acceptance report has no *Behavior changes* section to link.
- A bug that breaks a requirement sets the row to Partial or Unmet, and the evidence cell links its card.
- With a base pinned, the evidence cell can state whether the requirement already held at the base, or `unknown`.

## Nobody asked for this

List each delivered behavior inside the feature scope that no intent source supports: a bold title, the label *nobody asked for this*, a pinned link, and why no source covers it. A necessary implementation detail is not listed. When there is none, write one paragraph starting `None found:` with the scope inspected.

## Bug origins

In an acceptance report, *this change* means the feature's work: the linked commits and the traced feature code delivered in base..head. The chip line takes one of four origins:

- *new in this change* — absent at the base, present at the head.
- *pre-existing, made worse* — as in pr-review-guide.
- *from an unrelated commit* — absent at the base, present at the head, and evidence (a bisect, or linked work against blame) names an introducing commit outside the feature's work. The card adds `**Introduced by:**` after `**Trigger:**`, with that commit's SHA (7 to 40 hex characters) and what it changed.
- *no base pinned* — the front matter has no `base`, so the card attributes no origin. Every Base cell reads exactly `no base pinned`. This is the one exception to pr-review-guide's rule that every Base cell of a *suspected, not run* card starts with `predicted:`; the Head cells still start with `predicted:`.

With a base pinned, every card attributes its origin, and *no base pinned* fails the check. Without a base, every card uses *no base pinned*.

## Questions for the author

Keep two labeled lists, `**Spec owner:**` and `**Author:**`. The **spec owner** is the person who owns the intent source, such as the issue author or the ticket's reporter: Needs clarification rows and conflicting intent go to them. The **author** is whoever wrote the feature code, the same person the *ask the author* phrase means. Each question links its evidence: a source heading, an attention item, or a bug card. A list with no question states none, with the reason.

## Evidence and record

- `### Gaps` — unresolved evidence and scope limits, or an explicit none.
- `### Provenance` — each intent source with its collection time, the head, the base or `no base` with how it was found, local modifications, and relevant configuration.
- `### Feature scope` — the linked PRs and commits, the traced entry points, the interaction leads, and the attribution method.

## Page

For HTML, use pr-review-guide's [page notes](../../pr-review-guide/references/report-format.md#page). Each requirements group renders as its own table under its source heading. The [final structural check](../../pr-review-guide/references/report-format.md#final-structural-check) applies with `--acceptance` in place of `--review`, `--markdown-only` included.
