# PR review guide

Tell the reviewer what the change means and where to pay attention, then answer their questions in more depth. Maintain one current Markdown report and, when requested, its self-contained HTML companion, written in the shape of [report-format.md](references/report-format.md), starting from [report-template.md](references/report-template.md). This is review context, not an exhaustive defect list or merge verdict.

Follow the workflow below.

## Pin the review and map the change

1. Hold the kickoff round from [asking](../ASKING.md) first, before reading the diff, with the questions the request leaves open: how much codebase familiarity to assume; the deliverable, an HTML companion or text only (recommend text unless the reviewer asked for a page); the depth, *Full review* (recommended), which runs to the final report and delivers once, or *Overview only*, which delivers the overview and stops; and *Search for bugs?*, *Yes* (recommended) or *No*. Apply a choice the request states without asking; label a familiarity assumption as provisional until answered. Choose the report location. The first delivery states the applied choices in its `Kickoff:` line.
2. Resolve the PR's source repository, selected head SHA, and exact comparison base. For a PR, record the merge-base separately from the base branch's observed tip. Write the head and the merge-base as full SHAs in the report's front matter, as `head` and `base`, and the repository as `repository: owner/name`. When `report.md` sits outside the checkout that holds those commits, pass `--repo <checkout>` to every `render_page.py` run, `--check` included; [RENDERER.md](../RENDERER.md#code-peek) explains the code peek those commits enable, and an unavailable preview is a recorded gap. Verify the inspected source and record relevant local modifications, configuration, and dependency differences; inspect the pinned versions when local files differ. Record collection time and provenance for mutable PR descriptions, directly relevant linked tickets/specs, and prior reviews. Treat prior findings as leads to verify. Name inaccessible intent or source as a gap. Read the [local tool record](../TOOL-SETUP.md) if present. Select recorded operations that help this review, using the pinned revisions and each operation's actual inputs. Save useful outputs under `runs/tools/` beside the report, with the command, status, revision, and environment. Let the host manage independent work.
3. Read the changed-file inventory, the diff, and enough controlling code to trace the main flow yourself and name the parts and the main tradeoff: what moved, what it gives up, and the contract that now matters. Cite the lines you read. Create `report.md` at the location the caller supplied, else the routine location from [asking](../ASKING.md), with a nearby `review.md`, the review record, holding one run record per check and the consequential corrections; keep it as the reusable guide selected by the user.
4. **Enumerate, then rank.** Before naming parts, list every interaction the diff creates with existing code — a new caller or a second consumer of an existing producer, an override, a changed default, a copied block — and beside each what the existing analogues do that this one does not. Use applicable tool outputs as leads. Treat type-checker and linter diagnostics that differ between base and head as leads. Add an attention item when the inspected finding has a consequential effect or an unresolved question that changes the review action. Read tool results and recover from failed tools as [CODE-TOOLS.md](../CODE-TOOLS.md) says. Investigate symbols or scenarios that the selected operations did not cover. Cite consequential results with their command, conditions, and evidence limits. Compare relevant analogues when they exist: the nearest sibling and the path that defines the contract the user relies on. Inspect effective behavior through wrappers, inheritance, configuration, and intentional exceptions. Treat differences as leads; establish the contract and consumer consequence before calling one a defect. Distinguish new, pre-existing, and newly consequential defects using the same scenario at both snapshots. Rank the list by the consumer's next action if the entry is wrong. The list is *What to look at*, every item that merits it, with the *you decide*, *check it*, and *ask the author* items at the top; the bottom line and the rest of the report are written from the list, not the list from the report.
5. The selected depth sets the delivery.
   - **Full review:** send no overview reply. Continue through the steps below and deliver once, with the final reply.
   - **Overview only:** prepare a scoped report before deep traces or optional tool setup. State only what was inspected at the pinned head. Mark unopened parts *not yet inspected*, and label attention items with their actual evidence. Use the not-run paragraph in *Possible bugs* when no search ran. Run the mandatory final structural check after the last edit, then deliver the overview with its report link and material gaps. If further depth is unclear and useful, offer deeper work on all or selected parts using [asking](../ASKING.md). Resume from this report when the user chooses further work.

   When an open choice is answered later, continue from the existing report at the chosen depth; reuse the overview and evidence already delivered.

Done when a first report names every part, with its bottom line and items resting on lines you read, and the reviewer has the overview reply when they chose *Overview only*.

## Investigate the consequential questions

Use [CODE-TOOLS.md](../CODE-TOOLS.md) to select capabilities for the ranked questions, including test setup and the required report checker. Reuse existing preparation and authorization. Record relevant checks, failed operations, repairs or fallbacks, and the operations actually run. Ask only for a missing choice or permission when additional preparation is needed; continue independent work.

Read and apply [behavior comparison](../BEHAVIOR-COMPARISON.md) with the pinned base and head. Choose a changed contract, a second consumer of an existing producer, ownership/lifetime, error path, default, persistence effect, or propagation difference that could alter the reviewer's next action. Compare the same scenario through relevant unchanged producers/consumers and asynchronous or alternate paths.

Trace the main flow and the questions the changed lines settle. Use an [investigator](../INVESTIGATE.md) when a lifecycle, concurrency, public-boundary, or dependency question would benefit from a separate trace. Follow [native delegation](../WORKERS.md), framing the scenario to trace rather than a suspicion to confirm. Write each part from its evidence: the conditions it depends on, protection and failure boundaries, and documented rationale or labeled inference. Record why consequential concerns survived, changed, or dropped.

Write each consequential behavior with the [behavior template](references/behavior-template.md) and part shape of report-format.md. Link requirements to its named heading, compare scenarios through the consumer's next action, and link verification and attention items. Include relevant failure boundaries, compatibility and deployment effects; use a diagram when it resolves an ordering, state, or data-flow question. Put uncertainty beside the recommendation. Done when each consequential part has a supported comparison or a named gap, not merely a file summary.

### Compare requirements in both directions

Maintain the visible requirements table with the statuses of the shared [label catalog](../report-labels.json) and the column names in [report-format.md](references/report-format.md): intent source → requirement → named behavior → evidence or gap → next action. Use its linked, quoted citation form. Fulfillment and test execution are separate judgments. Conflicting intent stays visible; the reviewer does not choose what the author meant.

Also work from consequential delivered behavior back to intent. Label candidate requirements inferred from code. Additional effects with no supporting intent stay **intent-unconfirmed**; a necessary implementation detail or incomplete description alone does not establish scope creep. Continue this analysis when no spec is accessible.

### Interpret tests, then choose checks

Read relevant setup, assertions, mocks, and changed or removed expectations. Describe what the assertions establish under those conditions; names and passing counts cannot clear an unexercised scenario. Tests can share the implementation's mistaken assumption. Fake adapters and isolated models do not establish real backend or browser lifecycle behavior.

In the visible Verification section, distinguish **tests inspected**, **applicable recorded runs**, and **executions in this session** beside their claims. Use the template's result and evidence-origin columns; source inspection and proposed checks carry no execution result. Attach revision, configuration and scenario limits to each; retain commands, conditions, results and failed/blocked checks in the run record. Unknown CI conditions limit applicability. Proposed checks stay proposed until executed.

A recorded CI run at the pinned head is the suite result: cite it with its conditions. Execute only the focused check or authorized isolated experiment a named gap needs to explain behavior or settle an attention item's question — a benchmark for a claimed cost, a scenario no recorded run covers. A suspected defect goes to the search for bugs instead: record its line, condition, and predicted observable as a hypothesis in the review record, and let the search for bugs probe it and return the verdict. When the user skipped the search, the suspected defect becomes a *check it* item marked *reasoned, not run*. State the prediction first and keep experiments away from user work/data.

## Integrate, check, deliver

Update the Markdown as findings arrive; retain the inspected scope of an earlier overview in the review record. Stop a trace at an actionable explanation or explicit gap. Stop the deeper review when the consequential parts have explanations or named gaps, every changed file has a part and an honest inspection boundary, and further depth needs a new question or substantial experiment. Suggest further work when a consequential gap makes it useful. If interrupted earlier, label the report partial.

**Search for bugs.** When selected, load [find-bugs](../find-bugs/SKILL.md) and follow it as a scoped helper, yourself or through native delegation. Supply the pinned head and base, the report directory, the local tool record when available, applicable `runs/tools/` outputs, and investigation hypotheses; it saves its probes under the report's `runs/bugs/` and leaves the report to this skill. Scope the search to the report's changed parts and usable tools; with no setup record, use tools that need no new environment. Integrate returned defects as the [bug cards](references/report-format.md#bug-cards), with the consumer consequence explained. Link each card from a *you decide* or *check it* item and relevant author questions. With no defect found, name the source checks, probes, and remaining gaps; if the search could not run, state its reason. Update the verification table, attention list, and bottom line with the findings.

When the user skips the search for bugs, respect that choice and write `The search for bugs has not run: you chose to skip it.` as *Possible bugs*.

**Check the report after integrating findings.** Compare the bottom line, attention items, bug cards, author questions, and consequential parts with their evidence. Use a [second reader](../FRESH-REVIEW.md) when useful. Can a reviewer follow requirement → behavior/scenario → evidence → action, explain the main tradeoff and affected consumers, and identify material limits? Check diagram branches, failure boundaries, and claims about fulfillment, preservation, compatibility, and resolution. Fix, relabel, or cut unsupported claims. A material correction merits rechecking its evidence. Before every delivery, run `render_page.py <report.md> --check --review --sync-labels` after the last edit, including for text-only reports, as the [final structural check](references/report-format.md#final-structural-check) describes. Record the result and limits; repair structural failures before presenting the report as complete.

For HTML delivery, read and apply the [shared page workflow](../HTML-PAGES.md) with the page notes of report-format.md, and [reading-page guidance](../explain/references/reading-page.md) for a diagram or custom interaction.

Keep unresolved author questions in the report, with links to their evidence. When the user requests a PR comment, prepare the scoped draft naming the pinned head. Use existing authorization for its destination and content; if a required authorization is missing, show the draft and ask as [asking](../ASKING.md) describes. Post only when authorized and record the comment URL. A guide alone does not authorize approval, a request-changes review, or merge.

Keep the snapshot, consequential checks and results, corrections, and remaining gaps in the review record. Link the report by absolute path and state what the reviewer can use now.

## Deepen the existing guide

For a follow-up, resume here with the existing report and review record. Reuse the reviewer's familiarity, settled context, selected head/base, supported findings and tool-recovery choices. First compare the pinned head and base tip with the PR's current ones; when either moved, say which commits arrived and what they touch, and offer to re-pin (a new snapshot, with affected findings re-verified) or to continue on the pinned snapshot with that stated in the reply and the review record. Verify additional source against the snapshot in force; report updates never refresh the PR revision silently, and a re-pin reopens affected findings rather than every worker's return.

1. Scope the reviewer's question to the relevant part and its evidence gap. Use the bounded investigation above for only the additional evidence needed. A redirect changes the next question; a stop ends deeper work with any unfinished trace explicitly partial. Preserve findings and inspection gaps elsewhere.
2. For a hypothetical, distinguish the pinned PR's predicted behavior, the proposed code change and any observed experiment. Use the shared comparison through the affected consumer's next action. Keep proposed regression checks separate from executions. A hypothetical neither authorizes an application fix nor settles author intent. Offer a substantial experiment with its purpose, evidence limits and setup/runtime needs; preserve pending setup choices while continuing independent work.
3. Integrate the explanation into the existing part before answering, even when its conclusion is unchanged. Update Markdown, reconcile HTML when delivering it, and run the final structural check after the last edit. Then answer the scoped question with decisive evidence and the checked report link. Preserve useful named anchors and qualifications. On a new head, reopen affected findings and fulfillment judgments until rechecked; record what was rechecked and what still refers to the earlier snapshot. Keep the opening short; revise it only when attention priorities change.
4. For a material correction, replace the affected claim wherever it informs the current report, including requirements, recommendations and evidence summaries. Record the prior claim, replacement, reason and evidence in the review record, linked to the original execution records without rewriting their commands, conditions or results. Keep one current explanation; the review record audits conclusions rather than transcribing chat.

Record the question, additional evidence inspected, report sections changed, actual checks/results and remaining gaps. Run the final structural check after the last follow-up edit. Stop when the scoped question has an actionable explanation or explicit gap and the report is reconciled and structurally checked, or explicitly labeled unchecked because the checker could not run.
